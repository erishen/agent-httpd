# peer-network：先发现，再调用

局域网里可能同时跑着多个 lume 应用（`lume-blog`、`lume-lan`、`lume-scanner` …）。
它们各自的能力通过一个 MCP 桥挂到了你的工具表里，工具名形如
`<应用名>__<工具名>`，例如：

- `blog__blog.stats` — 博客统计
- `lan2__fs__read_text_file` — 另一个节点上的文件读取

## 什么时候用这个技能

**只有当你需要的资料不在本地工具能直接拿到的时候**：

- 用户问「博客最近写了什么」→ 用 `blog__blog.recent`
- 用户问「家里网络现在怎么样」→ 用 `lan__*` 里的设备/流量工具
- 用户问「局域网里还有哪些服务」→ 用 `_peers__discover`

## 第一步永远是发现

**不确定该用哪个工具时，先调 `_peers__discover`。** 它一次返回：

- 有哪些应用在线、各自负责什么
- 每个应用下有哪些工具、分别在什么场景用

不要做这些事（都是实测踩过的坑）：

- ❌ 用 `fs__list_directory` / `fs__search_files` 去翻别的应用的目录找答案
- ❌ 用 `memory__read_graph` 或 `read_file` 去读 `.data/*.db` 自己算数
- ❌ 凭记忆假设某个应用有什么能力

这些做法会浪费多轮工具调用，而且**读到的是文件不是应用语义**——比如
博客文章数应该问 `blog__blog.stats`，而不是去 SQLite 里 `COUNT(*)`。

## 调用约定

工具名两段式：`<应用名>__<工具名>`。应用名取自对端的 `PEER_NAME`，
可以从 `_peers__discover` 的输出里确认，不要自己拼。

参数统一放在 `arguments` 对象里（该对象的形状由对端工具定义）：

```
blog__blog.recent  {"arguments": {"limit": 5}}
```

## 边界

- **只读。** peer 通道默认只暴露只读工具；写/删除类会被策略过滤，并在
  `_peers__blocked` 里列出被拦的名字。不要尝试绕过——写操作要走各应用自己的
  后台（比如博客的后台 PIN）。
- **对端可能掉线。** 调用返回「不可达」时，如实告诉用户该应用当前连不上，
  不要编造数据，也不要改用 fs 去读它的数据库。
- **失败要暴露。** 某个 peer 工具报错就说明原因；不要吞掉错误假装成功。
