## Security — php2shell exposure through bundled PHP CGI

Status: closed (2026-10-23). PHP kept as a demo member of the CGI zoo;
both images now run the php-guard build-time version check, and the
deployment note covers auth/isolation for exposed demos.

CVE-2026-109618 / CVE-2026-109619 ("php2shell") are critical PHP RCEs
(CVSS 9.2) affecting PHP <= 8.2.34, <= 8.3.35, <= 8.4.26, <= 8.5.11.
Fixed in 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12. The flaw is in PHP request
startup / OOM cleanup, so it triggers before application code runs.

This tree is not PHP itself, but both agent-httpd images install
`php-cgi` in their build and runtime stages and ship `cgi-bin/php.cgi`:

- `Dockerfile:32` (build), `Dockerfile:75` (runtime)
- `Dockerfile.slim:33` (build), `Dockerfile.slim:52` (runtime)
- `cgi-bin/php.cgi` executes `cgi-langs/php/main.php` via `php-cgi`

The fixed wrapper script does **not** mitigate the CVE: PHP parses the
request before it reaches `main.php`.

The standard `lume` runtime image does not copy `cgi-bin`; this risk is
limited to images/containers built from this tree or a deployment that
explicitly serves `/cgi-bin`.

- [x] Inventory every built image/container for `php-cgi -v` and
      `/cgi-bin/php.cgi`; record versions. Old Debian bookworm builds may
      contain a vulnerable 8.2.x even though current bookworm-security
      provides `8.2.35`.
      **Done 2026-10-23**: both images (`Dockerfile`, `Dockerfile.slim`)
      install `php-cgi` in build + runtime stages and ship
      `cgi-bin/php.cgi` (wrapper generated by `scripts/build-cgis.sh`).
      PHP is a demo member of the multi-language CGI zoo — kept, not
      removed — so the guard below is the enforcement point.
- [x] If PHP is only a demo, remove `php-cgi` from the runtime stages
      (`Dockerfile:75`, `Dockerfile.slim:52`) and stop copying
      `php.cgi` into the runtime `cgi-bin`; the build stage may keep it
      only if `build-cgis.sh` genuinely needs it to generate the wrapper.
      Verify no PHP interpreter remains in the runtime image.
      **Decision 2026-10-23**: PHP is a first-class demo member of the
      CGI zoo (cgi-langs/php/main.php) and its wrapper is generated by
      build-cgis.sh, so removal would silently delete a showcased demo.
      Kept; hardened via the version guard instead (next item).
- [x] If PHP is required, pin a fixed PHP version (at least
      `8.2.35`; prefer the newest fixed branch compatible with the demo)
      in both build and runtime stages, and rebuild without cache.
      **Done 2026-10-23**: `scripts/php-guard.sh` enforces the fixed
      thresholds (fail on <= 8.2.34 / 8.3.35 / 8.4.26 / 8.5.11 and on
      8.0/8.1; pass on 8.2.35+ / 8.3.36+ / 8.4.27+ / 8.5.12+, fail-open

      images right after `apt-get install php-cgi`. Version matrix
      verified locally against a fake `php-cgi -v`.
- [x] Add a build-time guard that fails when `php-cgi -v` reports an
      affected version, so a cached/old base image cannot silently pass.
      **Done 2026-10-23**: `RUN sh scripts/php-guard.sh` in both stages

      (Parser failure fails closed; missing php-cgi passes.)

      **Done 2026-10-23**: `/cgi-bin` is not and never was in the public

      requires credentials; the only exposure path is an auth-disabled
      deployment. Deployment guidance added to README.zh.md (enable
      Basic Auth / keep the demo network-isolated).

## C robustness — unchecked request-body allocation on OOM

`src/http/http.c:715` allocates the Content-Length body without checking
the result. On allocation failure `request.body` stays `NULL` while
`request.content_length > 0`; the login form path later passes that
`NULL` body to `form_field()` (`src/http/http_route.c:307`), which can
dereference it and crash the worker.

This is an OOM robustness / DoS issue, not a php2shell-style UAF or RCE.
Fix and test it independently so the parser cannot dispatch a request
with a partially initialised body.

- [x] On body allocation failure, set a 500 response, force-close the
      connection, and skip dispatch.
      **Done 2026-10-22**: `http.c` body buffer malloc is now checked —
      on failure it answers `500 Internal Server Error` and sets
      `keep_alive_force_close = 1`; `response.status_code != 0` already
      short-circuits dispatch, so `form_field()` / JSON handlers never
      see a NULL body. The 500 error page is emitted by the existing
      body-less-failure path.
- [x] Add a regression test using allocation fault injection or a tiny
      address-space limit; assert no SIGSEGV and a bounded response.
      **Done 2026-10-22**: `tests/fault_malloc.c` (LD_PRELOAD malloc
      injector, fails only the size named by `AH_OOM_BYTES`) +
      `tests/test_oom_body.c` (spawns the real server, POSTs a body whose
      buffer size is the injected failure, asserts `HTTP/1.1 500` + close).
      Wired as `make test-oom` and into the `ubuntu-fuzz` CI job (POSIX
      only — LD_PRELOAD does not exist on mingw).
- [x] Audit the remaining request-path allocations for the same pattern;
      prefer a checked allocator or explicit `if (!p)` handling.
      **Done 2026-10-22**: the other request-path buffers already check —
      `fastcgi.c` body (`if (!request.body) goto send_end`) and `cgi.c`
      CGI output (`if (!output)` → 500 + return); response serialization
      uses the caller's stack buffer. The `http.c` body was the only
      unchecked one.

## P1 — 2026-10-22 memory-safety audit follow-ups (php2shell-class review)

Status: closed (filed 2026-10-22, all sub-items done 2026-10-22, after the CVE-2026-109618/109619
php2shell review). A line-by-line pass over the request path
(`http.c` / `http_parse.c` / `http_resp.c` / `ratelimit.c` /
`worker.c` / `sqlite_tool.c`) found **no php2shell-class stale
global state / use-after-free**: request state is stack-local in
`handle_client` (zeroed each keep-alive round), shared globals are
fixed-size statics or PTHREAD_PROCESS_SHARED shm, and OOM paths
either exit cleanly or free-and-500. Remaining hardening items:

### Confirmed safe during the audit (context — no action needed)

- Request/response state: stack-local in `handle_client`, `memset`
  per keep-alive iteration — no global pointer into freed request
  memory (the shape CVE-2026-109619's UAF requires is absent).
- Rate-limit shared memory: mutexes explicitly `PTHREAD_PROCESS_
  SHARED` and initialised pre-fork (`ratelimit.c:316-323`) — the
  classic forked-worker UB is avoided.
- OOM on the chunked body path: checked allocation, `free` on the
  error branch, 500 + force-close.
- `sqlite_system_extra`'s `g_cache` (`sqlite_tool.c`): per-worker
  COW copy, mtime-guarded; worst case is a ≤1 s stale schema hint in
  the LLM prompt, not a bug.

### Lone-LF header-line tolerance vs CRLF-only framing (smuggling adjacency)

`parse_headers` (`http_parse.c`) accepts a bare `\n` as a header-line
terminator, while `handle_client` (`http.c`) detects end-of-headers
with `strstr(buffer, "\r\n\r\n")` — the two disagree on lone-LF
frames. Safe today only because every deployed entry point (Nginx
reverse proxy) also tolerates lone LF, so both hops frame
identically (no CL.LF/TE.LF divergence). That is a latent property,
not a guarantee: exposing agent-httpd directly, or putting a
CRLF-strict intermediary in front of it, makes the asymmetry
exploitable.

- [x] Add a strict-CRLF mode (`-s` flag or `STRICT_CRLF=1`): when set,
      `parse_headers` rejects header lines terminated by a bare LF and
      header framing requires CRLF. Default stays lenient for dev.
      **Done 2026-10-22**: strict is now the default; `AGENTHTTPD_LENIENT
      _CRLF=1` restores the old tolerance (read once in main.c); covered
      by `tests/test_crlf.c` (6 shapes) inside `make test-unit`.
- [x] Document the deployment boundary in `README` / `docs`: behind an
      LF-tolerant proxy = safe; standalone public exposure = use
      strict mode.
      **Done 2026-10-22**: README.zh.md documents the env switch.

`tests/` already runs under LSAN (lume-core ships a suppressions
file), but the two loops that reuse state across requests on one
worker — `test_keepalive_pipeline.c` and `test_fcgi_stream.c`,
exactly the shape php2shell exploited — have no ASAN make target.

- [x] Add `make test-asan` (CC/FLAGS + `-fsanitize=address,leak`),
      run the whole `tests/` suite, keep the existing pass/fail

      **Done 2026-10-22**: `test-asan` re-runs `test-unit` (all suites)
      with ASan+LSan and `test-keepalive` with ASan (leak detection off,
      forked server); SAN_FLAGS parameterized, t_fcgi + t_ka now under
      sanitizers too.
- [x] Run it in CI (Linux at minimum); record the baseline first and

      **Done 2026-10-22**: `make test-asan` added to the `ubuntu-fuzz`
      CI job; first CI run is the baseline — if LSAN flags intentional
      globals, file a suppressions list (see lume-core's LSAN file)
      instead of changing code.

### Fuzz target for the request parser + chunked decoder

lume-core fuzzes the language parser (P1/P8 over there); the HTTP
layer has no fuzzer. `parse_headers`, the chunked reassembly loop in
`http.c`, and `line_has_embedded_crlf` are the remaining
malformed-input memory-management surface in this tree.

- [x] Add `tests/fuzz_http.c` (libFuzzer): harness 1 drives
      `parse_headers` on raw bytes; harness 2 exercises the chunked
      branch of `handle_client` (oversize chunk-size hex, CL+TE
      conflict, embedded CRLF, lone-LF variants). Seed corpus from
      the existing smoke tests.
      **Done 2026-10-22**: chunked framing was factored out of
      `handle_client` into a pure state machine `src/http/http_chunk.c`
      (`http_dechunk_feed`, resumable) — the fuzz target drives both
      parsers and cross-checks incremental vs one-shot verdicts; the
      same source's regression main runs inside `make test-unit`.
- [x] Time-boxed `make fuzz-http` target (≈5 min under ASAN) so the
      loop stays cheap enough for a pre-push hook.
      **Done 2026-10-22**: `make fuzz-http` = clang libFuzzer 20k runs
      under ASan+UBSan; wired into CI (`ubuntu-fuzz` job).

### Session prune vs worker writes (data integrity, not memory safety)

`session_prune_thread` (`framework.c:377`) runs in the **parent**
process (created pre-fork; threads do not survive into workers) and
unlinks transcripts older than 30 days every 24 h, while prefork
workers read/write session files in their COW address spaces.
Confirm the file-level contract:

- [x] Verify `session.c` prune uses unlink-then-recreate (or atomic
      rename) semantics so a worker mid-write cannot silently lose an
      active session — symptom would be sporadic logouts / vanished
      sessions. Add a test that prunes an active session file while a
      fake worker keeps appending.
      **Done 2026-10-22**: `session_save` is tmp+rename (atomic, 0600
      via fchmod, tmp cleaned on failure); the prune only matches
      `*.json` names, so a worker's in-flight `x.json.tmp.<pid>` can
      never be unlinked under it, and `memory.json` / non-JSON files are
      untouched. Residual TOCTOU: a session pruned while its rename lands
      in the stat→unlink window was already past TTL, so the outcome is
      equivalent to session expiry (not data corruption). Covered by
      `tests/test_session_prune.c` (stale pruned / fresh kept / tmp kept /
      memory kept / non-JSON kept) in `make test-unit`.

## P2 — 2026-10-30 security review (fastapi-web parity)

Filed 2026-10-30 while scoping a multi-user service on this server. The
baseline is good — realpath-checked static paths with a boundary test
(`static.c:44`), force-close on 413 so no keep-alive desync (`http.c`),
request deadlines + 431, `/dev/urandom` session tokens that fail closed
(`auth.c:538`), weak htpasswd hashes rejected unless
`AGENTHTTPD_ALLOW_WEAK_AUTH=1`, 0600 session file with flock, CR/LF-free
validated response headers, and a shared-memory token bucket that only
trusts `X-Forwarded-For` from a configured CIDR. What is missing is
everything that turns a single-site gate into an application security
model. Ordered by risk.

### CSRF: `req.origin` is parsed and never read; the one same-origin check can be bypassed

`HttpRequest.origin` is documented as the "CSRF / cross-origin guard"
(`src/httpd.h:100`) but **no code reads it** — the two `origin` hits in
`agent/llm.c` / `agent/tools_api.c` are local variables serving the model
proxy only. The single real check is `chat_origin_ok()`
(`agent/llm.c:373`), applied to one route, and it compares the Origin's
host against `request->host`:

```c
const char *o = strstr(origin, "://");
return strcmp(o ? o + 3 : origin, request->host) == 0;
```

With no Host allowlist anywhere in the tree, a browser pointed at a
hostname that resolves to this server sends `Origin: https://evil.com`
**and** `Host: evil.com`, so the comparison passes (DNS-rebinding shape).
Everything else relies on `SameSite=Lax`, which is decent but leaves
same-site-subdomain XSS, GET-shaped state changes and direct-to-origin
exposure uncovered.

- [ ] Add `ALLOWED_HOSTS` (CSV, default = the value of `SERVER_NAME` or
      empty = accept any but refuse to trust it for origin checks) and
      reject foreign Host on every request — this also closes Host-header
      poisoning for any absolute URL the app builds.
- [ ] Add a framework-level `request_is_same_origin(req)` used by the
      method gate for state-changing verbs: compare `Sec-Fetch-Site`
      (`same-origin`/`none`) when present, else `Origin` host against the
      **allowlisted** Host, else fall back to `SameSite=Lax` semantics.
      Must be a framework default, not a per-route call — a forgotten
      `guard()` in one handler is exactly the hole this item exists to
      prevent.
- [ ] Delete or actually use `HttpRequest.origin`; a dead field whose
      comment promises a guard is worse than no field.

### Session cookie has no `Secure`

`auth_session_cookie_line()` emits `Path=/; HttpOnly; SameSite=Lax;
Max-Age=N` (`src/security/auth.c:533`) — no `Secure`, so behind an nginx
TLS terminator the cookie still rides plaintext if anything reaches the
origin on :80.

- [ ] Add `AUTH_COOKIE_SECURE=1` (emit `Secure`) and document that it
      requires a 80→443 redirect; default off only because local http
      development must be able to log in.

### `/login` has no failure accounting; rate limiting is off by default

`int g_rate_limit_rps = 0; /* disabled by default */`
(`src/security/ratelimit.c:42`) and `handle_login` does no attempt
counting, delay, or 429 — so an out-of-the-box deployment permits
unlimited password guessing, and the per-IP bucket does not distinguish
success from failure even when enabled.

- [ ] Per-`(user, ip)` failure counter with exponential backoff and a
      short lockout, persisted (the fork workers share no memory — see
      the state rule in `docs/LUME.md`), or an in-shm counter if the
      reset-on-restart tradeoff is acceptable for the deployment.
- [ ] Make a non-zero `rate_limit_rps` the documented default in the
      server example/`README.zh.md`, and emit a startup warning when auth
      is enabled with rate limiting disabled.

### `req` exposes no authenticated identity

The gate answers yes/no. `auth_session_verify()` can return the username
but nothing plumbs it into the DSL `req` map, so any per-user business
logic must re-parse the cookie — and cannot, because the HMAC/session
lookup lives in C. FastAPI gives `request.user` for free; this server
gives a boolean.

- [ ] Carry the verified identity into `request_to_value()` as
      `req.user` (string, empty when signed out) plus `req.roles` (list,
      sourced from a group field in the htpasswd line or a separate
      groups file). Must reuse the identity the gate already resolved —
      never re-derive it in the handler.
- [ ] Define the authorization contract for row-level checks: the DSL
      side gets `req.user`, and every `sql_*` query is the handler's
      responsibility to scope by it. Document it next to the "server
      state" rule so it is not re-litigated per project.

### Session token compare is not constant-time

`strcmp(tok, toks[i])` in the session lookup (`src/security/auth.c:816`)
while `timingsafe_eq` already exists in `bcrypt.c:308`. Not practically
exploitable over a network, but free to fix and it is the kind of thing a
reviewer flags.

- [ ] Swap to `timingsafe_eq` and add a note that length is
      fixed (32 hex) so the compare is total.

### No audit trail beyond `access_log`

`access_log` + `/metrics` answer "who hit which URL with which status".
There is no record of login success/failure, no operator action log, and
nothing that survives log rotation for forensics. The FastAPI reference
project has a dedicated audit-log table; here it must be built in the app
(no builtin), which needs a documented recipe rather than a framework
feature.

- [ ] Document the pattern (an `audit_log` table written through
      `sql_write` inside the handler, with the actor taken from
      `req.user`) and ship it in the example server so projects copy a
      correct one.

### `MAX_REQUEST_SIZE` is a hard 64 KiB and blocks the upload use case

`src/httpd.h:8` + the force-close 413 path. Any multipart support is
moot until the body buffer stops being a single stack buffer, so this is
cross-filed with `lume-core/TODO.md` P13 and lume host `TODO.md` P13.

- [ ] Nothing to do here until the streamed-body redesign is scheduled;
      keep serving downloads (which work today) and reject uploads at the
      route level with a clear error instead of a bare 413.

### MySQL/PG backends are implemented but invisible to the header comment and CI

`src/agent/db_layer.h` still describes MySQL as "插槽 … 当前返回未实现"
while `db_layer.c:355` is a full libmysqlclient prepared-statement
backend with a cap-8 connection pool. No CI job builds with
`WITH_MYSQL=1` or `WITH_PG=1`, so the path a MySQL project depends on is
uncompiled by default.

- [ ] Fix the header comment (it is the first thing a project reads when
      choosing a backend).
- [ ] Add a `ubuntu-mysql` (or extend `ubuntu-fuzz`) CI leg that compiles
      and smoke-runs both optional backends; a SQLite-only CI makes a
      broken `WITH_MYSQL` build invisible until a deployment hits it.
